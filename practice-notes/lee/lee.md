# Git Study

## 1. 브랜치 동작 원리

### 1-1. 커밋과 브랜치

- **커밋(commit)**  
  - 특정 시점의 프로젝트 스냅샷과 메타데이터(메시지, 작성자, 부모 커밋)를 저장하는 단위이다.
- **브랜치(branch)**  
  - 가장 최신 커밋을 가리키는 이름이 있는 포인터이다.
  - 새 커밋이 생성될 때마다, 해당 브랜치는 그 커밋을 가리키도록 이동한다.
- **HEAD**  
  - 현재 작업 중인 브랜치를 가리키는 특수 포인터이다.

### 1-2. 브랜치를 사용하는 목적

- 기능, 버그 수정, 실험 등을 서로 독립된 작업 라인으로 분리한다.
- 메인 라인(`main`)을 항상 안정적인 상태로 유지할 수 있다.
- 문제가 발생했을 때, 특정 브랜치의 변경만 선택적으로 제거하거나 폐기할 수 있다.

## 2. GitHub Flow

### 2-1. 개요

GitHub Flow는 단순한 브랜치 전략으로, 다음 원칙을 따른다.

1. `main` 브랜치는 항상 배포 가능한 상태를 유지한다.
2. 새로운 작업은 항상 별도의 기능 브랜치(`feature/...`)에서 진행한다.
3. 기능 브랜치를 원격 저장소에 푸시한 뒤 Pull Request를 생성한다.
4. 코드 리뷰 및 검토를 거친 후 `main` 브랜치에 병합한다.
5. 필요 시 `main` 브랜치에서 배포를 수행한다.

### 2-2. 특징

- 브랜치 구조가 단순하고, 짧은 사이클의 작업에 적합하다.
- 기능별 변경 이력이 명확하게 분리된다.
- Pull Request를 중심으로 코드 리뷰와 변경 이력이 관리된다.

---

## 3. Pull Request(PR)와 코드 리뷰

### 3-1. Pull Request

- 한 브랜치의 변경 사항을 다른 브랜치(주로 `main` 또는 `develop`)에 병합하기 전에 제안하는 절차이다.
- 변경된 파일, 커밋 목록, 설명, 관련 이슈 등을 한 곳에서 확인할 수 있다.
- 병합 전 검토, 토론, 승인 과정을 강제할 수 있다.

### 3-2. 코드 리뷰

- Pull Request에 포함된 코드를 검토하고 피드백을 제공하는 과정이다.
- 목적
  - 잠재적인 버그, 성능 저하, 보안 문제 등을 사전에 발견한다.
  - 팀 내 코드 스타일과 설계 기준을 일관되게 유지한다.
  - 코드와 도메인 지식을 팀 구성원 간에 공유한다.

### 3-3. PR 작성 시 포함할 정보 예시

- 변경 목적 및 배경
- 주요 변경 내용 요약
- 테스트 수행 여부 및 방법
- 리뷰어가 중점적으로 확인해야 할 부분

## 4. 머지 충돌과 충돌 마커

### 4-1. 머지 충돌(Conflict)

- 서로 다른 브랜치에서 같은 파일의 같은 영역이 서로 다르게 수정되었을 때 발생한다.
- Git이 자동으로 어느 변경을 선택해야 할지 결정할 수 없는 상태를 의미한다.

### 4-2. 충돌 마커 형식

Git은 충돌이 발생한 파일 내부에 다음 형태의 마커를 삽입한다.


```text
<<<<<<< HEAD
현재 브랜치 내용
=======
다른 브랜치 내용
>>>>>>> feature/signup
```

- `<<<<<<< HEAD`  
  - 현재 기준이 되는 브랜치(HEAD)의 내용을 나타낸다.
- `=======`  
  - 두 변경 내용을 구분하는 경계이다.
- `>>>>>>> feature/signup`  
  - 병합 대상이 되는 다른 브랜치의 내용을 나타낸다.

### 4-3. 충돌 해결 절차

1. 충돌 마커가 포함된 파일을 열어, 최종적으로 유지할 코드를 결정한다.
2. 선택된 코드만 남기고, `<<<<<<<`, `=======`, `>>>>>>>` 마커를 모두 제거한다.
3. 수정된 파일을 저장한다.
4. `git add <파일>`로 변경을 스테이징한다.
5. `git commit`으로 충돌 해결 커밋을 생성한다.

## 5. `reset`, `revert`, `stash`

### 5-1. 개요

아래 세 명령어는 작업 이력이나 작업 중인 변경을 조정할 때 사용한다.

| 명령어   | 동작 요약                                                | 주 사용 위치       |
|----------|----------------------------------------------------------|--------------------|
| `reset`  | 브랜치 포인터를 과거 커밋으로 이동 (히스토리 재작성 가능) | 로컬 브랜치        |
| `revert` | 특정 커밋의 변경을 반대로 적용하는 새 커밋 생성          | 공유 브랜치(원격)  |
| `stash`  | 워킹 디렉터리와 스테이징 변경을 임시 영역에 저장         | 브랜치 전환 전 등  |

### 5-2. `git reset`

- 브랜치가 가리키는 커밋을 지정한 커밋으로 이동시킨다.
- 옵션에 따라 워킹 디렉터리와 스테이징 영역의 상태도 함께 변경된다.

자주 사용하는 예:

```bash
git reset --soft HEAD~1
```

- `HEAD~1`: 현재 커밋의 직전 커밋
- `--soft`: 브랜치 포인터만 이동시키고, 워킹 디렉터리와 스테이징 영역은 그대로 유지한다.  
  → 최근 커밋을 취소하되, 변경 내용은 유지하고 싶을 때 사용한다.

### 5-3. `git revert`

- 지정한 커밋이 도입한 변경을 반대로 적용하는 새 커밋을 생성한다.
- 기존 히스토리를 유지하면서 “취소” 이력을 명확히 남길 수 있다.
- 원격 저장소에 이미 푸시된 커밋을 되돌릴 때 사용하기 적합하다.

예:

```bash
git revert <커밋 해시>
```

### 5-4. `git stash`

- 현재 워킹 디렉터리와 스테이징 영역의 변경을 임시로 저장하고, 작업 트리를 깨끗한 상태로 되돌린다.
- 브랜치를 전환해야 하지만 아직 커밋하고 싶지 않은 변경이 있을 때 사용한다.

예:

```bash
git stash          # 현재 변경을 stash에 저장
git switch main    # 다른 작업 수행
...
git switch feature/원래브랜치
git stash pop      # 저장해 둔 변경 복원 후 stash에서 제거
```

## 6. 주요 명령 사용 시나리오

### 6-1. `git commit --amend` (최근 커밋 수정)

- 가장 최근 커밋의 메시지 또는 포함된 변경 내용을 수정할 때 사용한다.
- 아직 원격 저장소에 푸시하지 않은 커밋에 사용하는 것이 일반적이다.

```bash
git commit --amend
```

### 6-2. `git reset --soft HEAD~1` (로컬 커밋 취소 + 변경 유지)

- 방금 만든 커밋을 취소하고, 해당 커밋의 변경 내용은 워킹 디렉터리에 남긴다.
- 커밋을 다시 나누거나 메시지를 재구성하고 싶을 때 사용한다.

### 6-3. `git revert` (원격에 푸시된 커밋 취소)

- 이미 공유된 브랜치에 포함된 커밋을 취소할 때 사용한다.
- 다른 개발자의 로컬 히스토리를 깨뜨리지 않고 변경을 되돌릴 수 있다.

예:

```bash
git revert abc1234
git push origin main
```

### 6-4. `git stash` / `git stash pop` (작업 보관 후 전환)

- 진행 중인 변경을 임시로 저장한 뒤, 다른 브랜치로 전환해야 할 때 사용한다.

예:

```bash
git stash
git switch main
# 긴급 이슈 처리
git switch feature/원래브랜치
git stash pop
```

## 7. 협업 중 문제 발생 시 기록 방법

협업 환경에서는 문제 상황과 해결 과정을 재현 가능하게 기록해 두는 것이 중요하다.

### 7-1. 기록에 포함할 요소

1. **상황 요약**
   - 문제가 발생한 브랜치, 시점, 증상
2. **재현 절차**
   - 실행한 Git 명령과 순서
   - 재현 가능한 명령 시퀀스 예시
3. **조사 내용**
   - `git log`, `git reflog` 등으로 확인한 이력 정보
4. **해결 절차**
   - 사용한 명령 (`reset`, `revert`, 수동 충돌 해결 등)
   - 변경된 브랜치 상태
5. **후속 조치**
   - 팀원이 수행해야 할 작업 (`pull`, 브랜치 정리 등)

이 정보를 노션, 위키, 팀 문서 등에 명령어와 함께 정리해 두면, 유사한 문제가 재발했을 때 빠르게 복구 절차를 반복할 수 있다.
