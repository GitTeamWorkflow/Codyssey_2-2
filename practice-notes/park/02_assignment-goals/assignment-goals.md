# 과제 목표 정리

## 1. 과제 목표 개요

이 과제의 목표는 Git과 GitHub를 이용한 팀 협업 흐름을 이해하고, 실제 협업 중 발생할 수 있는 문제를 설명하고 해결할 수 있도록 하는 것이다.

과제를 마친 후에는 다음 내용을 스스로 설명할 수 있어야 한다.

- 브랜치가 내부적으로 어떻게 동작하는지
- 왜 브랜치를 나눠서 작업하는지
- GitHub Flow가 무엇인지
- Pull Request(PR)의 목적과 코드 리뷰의 가치
- 충돌이 발생하는 이유와 충돌 마커의 의미
- `reset`, `revert`, `stash`의 차이
- 협업 중 발생한 문제를 기록하고 재현 가능한 방식으로 해결하는 방법

---

## 2. 브랜치의 내부 동작

Git에서 브랜치는 독립된 작업 공간처럼 보이지만, 내부적으로는 특정 commit을 가리키는 포인터이다.

예를 들어 `main` 브랜치가 최신 commit `C3`을 가리키고 있다고 하면 다음과 같이 표현할 수 있다.

```text
C1 --- C2 --- C3
              ↑
             main
```

여기서 새로운 브랜치 `feature/login`을 만들면, 처음에는 `main`과 같은 commit을 가리킨다.

```text
C1 --- C2 --- C3
              ↑
             main
              ↑
        feature/login
```

이후 `feature/login` 브랜치에서 새 commit을 만들면 `feature/login` 브랜치만 앞으로 이동한다.

```text
C1 --- C2 --- C3
              ↑
             main
               \
                C4
                ↑
          feature/login
```

즉, 브랜치는 파일을 복사해서 새 공간을 만드는 것이 아니라, commit을 가리키는 포인터를 만들어 작업 흐름을 분리하는 방식이다.

---

## 3. 브랜치를 나눠서 작업하는 이유

브랜치를 나누는 이유는 안정적인 기준 브랜치를 보호하면서 여러 작업을 동시에 진행하기 위해서이다.

`main` 브랜치는 항상 실행 가능하고 제출 가능한 상태를 유지해야 한다. 그런데 모든 팀원이 `main`에서 직접 작업하면 다음과 같은 문제가 생길 수 있다.

- 아직 완성되지 않은 코드가 `main`에 들어갈 수 있다.
- 다른 팀원의 작업과 충돌이 발생할 수 있다.
- 오류가 있는 코드가 기준 브랜치에 반영될 수 있다.
- 누가 어떤 작업을 했는지 추적하기 어렵다.

따라서 기능 추가, 문서 수정, 버그 수정 등은 별도 브랜치에서 진행한다.

예시:

```text
main
├── feature/login
├── docs/update-readme
└── fix/navbar-error
```

작업이 완료된 브랜치만 Pull Request를 통해 검토 후 `main`에 병합한다.

---

## 4. GitHub Flow란?

GitHub Flow는 `main` 브랜치를 중심으로 작업 브랜치와 Pull Request를 사용하는 협업 전략이다.

기본 흐름은 다음과 같다.

```text
main 최신화
→ 작업 브랜치 생성
→ 작업 및 commit
→ 작업 브랜치 push
→ Pull Request 생성
→ Review 및 Approve
→ main에 merge
```

명령어 예시는 다음과 같다.

```bash
git switch main
git pull origin main

git switch -c docs/update-readme

# 파일 수정 후
git add .
git commit -m "[Docs] README 수정"
git push -u origin docs/update-readme
```

이후 GitHub에서 Pull Request를 생성하고, 팀원의 리뷰와 승인을 받은 뒤 `main`에 병합한다.

---

## 5. 팀 협업에서 GitHub Flow가 필요한 이유

GitHub Flow가 필요한 이유는 팀 프로젝트에서 `main` 브랜치를 안정적으로 유지하기 위해서이다.

GitHub Flow를 사용하면 다음과 같은 장점이 있다.

| 장점 | 설명 |
|---|---|
| 안정성 유지 | `main`에는 검토된 작업만 병합된다. |
| 작업 분리 | 기능, 문서, 수정 작업을 브랜치별로 나눌 수 있다. |
| 리뷰 가능 | PR을 통해 팀원이 변경사항을 확인할 수 있다. |
| 이력 관리 | 누가 어떤 작업을 했는지 기록으로 남는다. |
| 충돌 관리 | 병합 전에 충돌을 확인하고 해결할 수 있다. |

과제에서는 `main` 직접 push를 금지하고 PR을 통해서만 병합하도록 설정함으로써 GitHub Flow를 실습한다.

---

## 6. PR(Pull Request)의 목적

Pull Request는 작업 브랜치의 변경사항을 `main` 브랜치에 병합해도 되는지 요청하는 과정이다.

예를 들어 `docs/update-readme` 브랜치에서 README를 수정했다면, PR은 다음 의미를 가진다.

```text
docs/update-readme 브랜치의 변경사항을 main에 병합하고 싶습니다.
검토해 주세요.
```

PR을 통해 확인할 수 있는 내용은 다음과 같다.

- 어떤 파일이 수정되었는지
- 어떤 코드가 추가되거나 삭제되었는지
- 작업 목적이 무엇인지
- 관련 Issue가 무엇인지
- 팀원의 리뷰 의견
- Approve 여부

---

## 7. 코드 리뷰의 가치

코드 리뷰는 단순히 틀린 코드를 찾는 과정이 아니다. 팀원이 작업 내용을 이해하고, 더 나은 방향으로 개선하기 위한 협업 과정이다.

코드 리뷰의 가치는 다음과 같다.

| 가치 | 설명 |
|---|---|
| 오류 예방 | 실수나 버그를 main 병합 전에 발견할 수 있다. |
| 품질 향상 | 코드 구조, 문서 표현, 네이밍 등을 개선할 수 있다. |
| 지식 공유 | 팀원이 서로의 작업 내용을 이해할 수 있다. |
| 책임 분산 | 한 명이 모든 결정을 하지 않고 팀 단위로 검토한다. |
| 협업 기록 | 리뷰 내용이 GitHub에 기록으로 남는다. |

과제에서 최소 1명 이상의 Approve를 요구하는 이유는 이러한 코드 리뷰 과정을 경험하기 위해서이다.

## 8. 충돌이 발생하는 이유

충돌은 서로 다른 브랜치에서 같은 파일의 같은 부분을 다르게 수정했을 때 발생한다.

예를 들어 `main` 브랜치에서 README의 같은 줄을 수정했고, `feature/park` 브랜치에서도 같은 줄을 다르게 수정했다면 Git은 어떤 내용을 선택해야 할지 판단하지 못한다.

이때 conflict가 발생한다.

예시 상황:

```text
main 브랜치:
README.md의 3번째 줄 수정

feature/park 브랜치:
README.md의 3번째 줄을 다르게 수정
```

이 상태에서 merge를 하면 Git은 자동으로 병합하지 못하고 사용자가 직접 선택하도록 충돌 표시를 남긴다.

---

## 9. 충돌 마커의 의미

충돌이 발생하면 파일 안에 다음과 같은 마커가 생긴다.

```text
<<<<<<< HEAD
현재 브랜치의 내용
=======
병합하려는 브랜치의 내용
>>>>>>> feature/park
```

각 마커의 의미는 다음과 같다.

| 마커 | 의미 |
|---|---|
| `<<<<<<< HEAD` | 현재 브랜치의 변경 내용 시작 |
| `=======` | 두 변경 내용을 구분하는 경계 |
| `>>>>>>> 브랜치명` | 병합하려는 브랜치의 변경 내용 끝 |

예시:

```text
<<<<<<< HEAD
우리 팀은 GitHub Flow를 사용한다.
=======
우리 팀은 Git Flow 전략을 사용한다.
>>>>>>> feature/park
```

이 경우 둘 중 하나를 선택하거나, 두 내용을 적절히 합쳐야 한다.

수정 예시:

```text
우리 팀은 GitHub Flow를 기반으로 브랜치 전략을 사용한다.
```

충돌을 해결한 뒤에는 다음 명령어를 실행한다.

```bash
git add README.md
git commit
```

## 10. reset, revert, stash의 차이

Git에서 `reset`, `revert`, `stash`는 모두 작업 상태를 되돌리거나 임시 저장할 때 사용하지만 목적이 다르다.

| 명령어 | 목적 | 특징 |
|---|---|---|
| `reset` | commit 이력을 특정 시점으로 되돌림 | 기존 commit 이력을 바꿀 수 있음 |
| `revert` | 특정 commit을 취소하는 새 commit 생성 | 이력을 유지하면서 안전하게 되돌림 |
| `stash` | 아직 commit하지 않은 변경사항을 임시 저장 | 브랜치 이동 전 작업물을 잠시 보관 |

---

## 11. reset, revert, stash 비교

| 상황 | 추천 명령어 | 이유 |
|---|---|---|
| 아직 push하지 않은 commit을 취소하고 싶을 때 | `reset` | 로컬 이력을 정리할 수 있다. |
| 이미 push한 commit을 취소하고 싶을 때 | `revert` | 공유 이력을 안전하게 유지할 수 있다. |
| 작업 중인 변경사항을 잠시 숨기고 싶을 때 | `stash` | commit 없이 임시 저장할 수 있다. |
| 잘못된 commit을 기록을 남기고 되돌리고 싶을 때 | `revert` | 취소 작업도 commit으로 남는다. |
| 브랜치를 바꿔야 하는데 수정사항이 남아 있을 때 | `stash` | 작업물을 임시 저장하고 이동할 수 있다. |

## 12. 협업 중 문제 해결 기록의 중요성

팀 협업 중에는 충돌, 실수 commit, 잘못된 merge, push 실패 같은 문제가 발생할 수 있다.

중요한 것은 문제를 그냥 해결하는 것이 아니라, 어떤 문제가 있었고 어떻게 해결했는지 기록하는 것이다.

기록을 남기면 다음과 같은 장점이 있다.

- 같은 문제가 다시 발생했을 때 빠르게 해결할 수 있다.
- 팀원이 문제 원인을 이해할 수 있다.
- 과제 제출 시 문제 해결 과정을 증명할 수 있다.
- 협업 과정의 책임과 이력이 명확해진다.

## 13. 문제 해결 기록 작성 방식

문제가 발생했을 때는 다음 구조로 기록한다.

```md
## 문제 상황

- 어떤 작업 중 문제가 발생했는지 작성한다.

## 원인

- 왜 문제가 발생했는지 작성한다.

## 해결 과정

- 어떤 명령어를 사용했는지 작성한다.
- 어떤 파일을 수정했는지 작성한다.

## 결과

- 문제가 해결되었는지 확인한 내용을 작성한다.

## 재현 및 예방 방법

- 같은 문제가 다시 발생했을 때 어떻게 해결할 수 있는지 작성한다.
- 앞으로 어떻게 예방할 수 있는지 작성한다.
```

## 14. 문제 해결 기록 예시: Merge Conflict

```md
## 문제 상황

`feature/park` 브랜치에서 `main` 브랜치 내용을 merge하는 과정에서 README.md 파일에 conflict가 발생했다.

## 원인

`main` 브랜치와 `feature/park` 브랜치에서 README.md의 같은 줄을 서로 다르게 수정했기 때문에 Git이 자동으로 병합하지 못했다.

## 해결 과정

1. 충돌 파일을 확인했다.

```bash
git status
```

2. README.md 파일에서 충돌 마커를 확인했다.

```text
<<<<<<< HEAD
현재 브랜치 내용
=======
병합 대상 브랜치 내용
>>>>>>> main
```

3. 필요한 내용을 직접 선택하여 수정했다.
4. 수정한 파일을 staging area에 추가했다.

```bash
git add README.md
```

5. merge commit을 생성했다.

```bash
git commit
```

## 결과

README.md의 충돌이 해결되었고, `main` 브랜치의 최신 내용이 `feature/park` 브랜치에 반영되었다.

## 재현 및 예방 방법

작업 시작 전 항상 `main` 브랜치를 최신화하고, 장시간 브랜치를 방치하지 않는다.

```bash
git switch main
git pull origin main
```

## 15. 문제 해결 기록 예시: 실수 commit 되돌리기

```md
## 문제 상황

작업 브랜치에서 잘못된 파일을 포함하여 commit을 생성했다.

## 원인

`.DS_Store`와 같이 프로젝트에 필요 없는 파일을 확인하지 않고 `git add .` 명령어로 함께 추가했다.

## 해결 과정

아직 원격 저장소에 push하지 않은 commit이므로 `reset`을 사용하여 commit을 취소했다.

```bash
git reset --mixed HEAD~1
```

필요 없는 파일을 `.gitignore`에 추가했다.

```bash
echo ".DS_Store" >> .gitignore
```

다시 필요한 파일만 staging area에 추가했다.

```bash
git add README.md .gitignore
git commit -m "[Docs] README 수정 및 .DS_Store ignore 추가"
```

## 결과

불필요한 파일을 제외하고 올바른 commit을 다시 생성했다.

## 재현 및 예방 방법

commit 전 항상 다음 명령어로 변경 파일을 확인한다.

```bash
git status
```

## 16. 최종 요약

이 과제의 핵심은 Git 명령어를 외우는 것이 아니라, Git과 GitHub가 팀 협업에서 어떤 역할을 하는지 이해하는 것이다.

정리하면 다음과 같다.

- 브랜치는 commit을 가리키는 포인터이다.
- 브랜치를 나누면 `main`을 안정적으로 유지하면서 여러 작업을 동시에 진행할 수 있다.
- GitHub Flow는 작업 브랜치, Pull Request, Review, Merge를 중심으로 한 협업 전략이다.
- PR은 변경사항을 검토하고 안전하게 `main`에 병합하기 위한 요청이다.
- 코드 리뷰는 오류 예방, 품질 향상, 지식 공유에 도움이 된다.
- 충돌은 같은 파일의 같은 부분을 서로 다르게 수정했을 때 발생한다.
- 충돌 마커는 현재 브랜치와 병합 대상 브랜치의 차이를 보여준다.
- `reset`은 이력을 되돌리고, `revert`는 되돌리는 새 commit을 만들며, `stash`는 작업 중인 변경사항을 임시 저장한다.
- 협업 중 발생한 문제는 원인, 해결 과정, 결과를 기록해야 재현 가능하고 설명 가능한 협업이 된다.
